# speechParser

Telegram-бот и CLI-клиент для расшифровки записей МТС Линк и загруженных аудио/видео файлов. Клиенты запускаются локально; загрузка записи по ссылке и распознавание выполняются на отдельном сервере. Результат — текстовый файл `.txt`.

Если воркер уже работает, начни с [настройки CLI](#локальный-cli-большие-файлы-без-telegram) или [Telegram-бота](#локальный-бот). Для нового сервера смотри [запуск воркера](#обработчик-на-vps) и [подключение через SSH](#подключение-клиентов-через-ssh-туннель).

## Архитектура

| Компонент | Назначение | Зависимости |
|---|---|---|
| `cli.py` | Отправляет файл или ссылку воркеру, показывает прогресс и сохраняет текст локально | `requirements-client.txt` |
| `bot.py` | Принимает ссылки и файлы в Telegram, отправляет задания воркеру и возвращает `.txt` в чат | `requirements-bot.txt` |
| `worker_server.py` | На VPS принимает задания, скачивает записи МТС Линк и выполняет распознавание | `requirements-worker.txt` |
| `transcribe.py` | Выполняет самостоятельное распознавание на текущем компьютере | `requirements-worker.txt` |

CLI и бот используют общий HTTP-клиент `processor_client.py` и один API воркера. Для CLI и бота достаточно Python 3.10+; Docker-образ воркера использует Python 3.12. FFmpeg и модель Whisper нужны на машине, выполняющей распознавание. Для приватных записей cookie `MTS_SESSION_ID` задаётся на VPS.

## Обработчик на VPS

Установи Docker Engine с Compose plugin на VPS с Debian/Ubuntu и клонируй репозиторий. Для установки Docker на Ubuntu в репозитории есть [install-docker-ubuntu.sh](install-docker-ubuntu.sh). Создай конфигурацию worker:

```bash
cp .env.server.example .env.server
chmod 600 .env.server
openssl rand -hex 32
nano .env.server
```

Впиши сгенерированный секрет в `PROCESSOR_API_KEY`. Для приватных записей добавь cookie `access` в `MTS_SESSION_ID`. `PROCESSOR_HOST` в файле оставь `127.0.0.1`: Compose переопределяет его внутри контейнера, а порт на VPS публикует только на loopback.

Если worker уже запущен напрямую из `venv`, сначала останови его, чтобы освободить порт `8080`.

Сборка образа и запуск worker выполняются одной командой:

```bash
docker compose up -d --build
```

Проверить запуск и смотреть логи можно так:

```bash
docker compose ps
docker compose logs -f worker
```

Контейнер перезапускается автоматически. Модели Whisper сохраняются в `whisper_cache`, временные задания — в `processor_data`. Порт доступен на VPS только через `127.0.0.1:8080`, поэтому SSH-туннель и локальный reverse proxy работают без изменений.

### Запуск воркера без Docker

На VPS с Debian/Ubuntu установи Python, Git и FFmpeg, затем подготовь виртуальное окружение в каталоге репозитория:

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip ffmpeg git
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements-worker.txt
```

Создай `.env.server` как описано выше. Для прямого запуска оставь `PROCESSOR_HOST=127.0.0.1`, затем загрузи переменные и запусти обработчик:

```bash
set -a
source .env.server
set +a
python worker_server.py
```

### Подключение клиентов через SSH-туннель

На компьютере с CLI или ботом открой SSH-туннель к VPS:

```bash
ssh -N -L 18080:127.0.0.1:8080 vps_sp
```

Здесь `vps_sp` — SSH alias из `~/.ssh/config`; вместо него можно указать `user@server`. Оставь туннель запущенным и укажи в локальном `.env` `PROCESSOR_URL=http://127.0.0.1:18080`. Передача между компьютером и VPS идёт внутри SSH-соединения. CLI и бот используют один и тот же адрес и API-ключ.

### Другие способы подключения

Если у VPS есть домен, можно настроить HTTPS reverse proxy, например Caddy:

```caddy
processor.example.com {
	reverse_proxy 127.0.0.1:8080
}
```

Без собственного домена можно использовать Tailscale Serve: подключи VPS и компьютер с клиентом к одной tailnet-сети, затем на VPS выполни:

```bash
sudo tailscale serve --bg http://127.0.0.1:8080
tailscale serve status
```

Tailscale покажет HTTPS-адрес VPS вида `https://имя-машины.имя-сети.ts.net`. Укажи его в `PROCESSOR_URL` в локальном `.env`. Этот адрес доступен только устройствам той же tailnet-сети, поэтому Tailscale должен быть подключён и на VPS, и на компьютере с CLI или ботом.

На компьютере с CLI или ботом установи клиент Tailscale. Для Ubuntu и Debian:

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale status
```

Открой ссылку, показанную командой `tailscale up`, и войди в ту же tailnet, что и на VPS. Если VPS добавлен в tailnet под другим аккаунтом, администратор этой сети должен пригласить аккаунт компьютера. В выводе `tailscale status` должны отображаться оба устройства. Для Windows и macOS установщик доступен на [странице загрузки Tailscale](https://tailscale.com/download).

При использовании Caddy укажи в `PROCESSOR_URL` публичный HTTPS-домен. Не открывай порт `8080` напрямую в интернет: API-ключ защищает запросы, но не шифрует передаваемые аудио и ключ.

## Локальный CLI: большие файлы без Telegram

На компьютере достаточно Python 3.10+ и двух клиентских зависимостей. FFmpeg, Whisper и Telegram для CLI не нужны:

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements-client.txt
```

В `.env` в каталоге проекта задай адрес запущенного воркера и его API-ключ:

```dotenv
PROCESSOR_URL=http://127.0.0.1:18080
PROCESSOR_API_KEY=тот-же-секрет-что-на-сервере
WHISPER_MODEL=large-v3
TRANSCRIPTION_TIMEOUT_SECONDS=10800
```

Переменные окружения также поддерживаются и имеют приоритет над `.env`. Для указанного адреса открой SSH-туннель из раздела выше. `BOT_TOKEN` и `ALLOWED_USER_ID` клиенту не нужны.

```bash
python cli.py "/path/to/large video.mp4"
python cli.py recording.mkv --output transcripts/meeting.txt --model large-v3
python cli.py "https://my.mts-link.ru/1/2/record-new/3" -o meeting.txt
python cli.py recording.mp4 --timeout 21600
python cli.py recording.mp4 --url http://127.0.0.1:18080
python cli.py recording.mp4 -o meeting.txt --force
python cli.py --help
```

| Аргумент | Назначение |
|---|---|
| `input` | Путь к локальному файлу или ссылка на запись МТС Линк |
| `-o`, `--output` | Путь для сохранения текста |
| `--model` | Модель Whisper; по умолчанию `WHISPER_MODEL`, а при его отсутствии — `medium` |
| `--url` | Адрес воркера для этого запуска; переопределяет `PROCESSOR_URL` |
| `--timeout` | Общий лимит времени в секундах; по умолчанию `TRANSCRIPTION_TIMEOUT_SECONDS`, а при его отсутствии — `10800` |
| `--force` | Разрешить замену существующего файла результата |
| `-h`, `--help` | Справка по аргументам |

Поддерживаются `.mp4`, `.mp3`, `.wav`, `.m4a`, `.ogg`, `.webm`, `.mkv`, `.avi`, `.mov`. Воркер распознаёт русскую речь. Ссылки МТС Линк принимаются в формате `https://my.mts-link.ru/<id>/<id>/record-new/<session>` с необязательным `/record-file/<record>`.

По умолчанию результат сохраняется рядом с исходником с расширением `.txt`; для ссылки — `transcript_<session>[_<record>].txt` в текущем каталоге. Существующий результат заменяется только с `--force` и только после получения нового текста. При ошибке или отмене без готового текста прежний файл сохраняется. Путь результата выводится в stdout, прогресс загрузки и статусы — в stderr.

Первый Ctrl+C запрашивает отмену, дожидается остановки на сервере и сохраняет готовую часть текста, если она есть. При прерывании загрузки готовой расшифровки ещё нет. Второй Ctrl+C завершает ожидание. Код завершения: `0` — готово, `1` — ошибка, `2` — ошибка аргументов, `130` — отмена. Общий `--timeout` включает передачу файла, очередь и обработку; по умолчанию — три часа. Серверный `TRANSCRIPTION_TIMEOUT_SECONDS` отдельно ограничивает обработку запущенного задания.

Файл передаётся блоками по 64 KiB, без загрузки целиком в RAM и без дополнительной локальной копии видео. Воркер разрешает до **10 ГБ** по умолчанию. CLI проверяет серверный лимит перед отправкой; со старым воркером без `/limits` ограничение проверяется при POST.

Лимит задаётся в `.env.server` через `MAX_UPLOAD_GB` в десятичных гигабайтах: **1 ГБ = 1000 МБ**. Допускаются дробные значения с точкой, например:

```dotenv
MAX_UPLOAD_GB=0.25
```

Это разрешает файлы до **250 МБ** включительно. Для 10 ГБ задай `MAX_UPLOAD_GB=10`. После изменения пересобери воркер, когда текущие задания завершатся:

```bash
docker compose up -d --build worker
```

При запуске без Docker перезапусти `worker_server.py` с обновлённым окружением. Для больших файлов на VPS нужно свободное место под исходное видео, извлечённое аудио и рабочие части. Если используется reverse proxy, настрой также его ограничение размера тела запроса и таймауты; для Nginx, например, `client_max_body_size 10g;`. SSH-туннель подключается напрямую к воркеру. Прерванная загрузка удаляется на сервере; продолжение с места обрыва и автоматическая повторная отправка не предусмотрены. После получения результата CLI удаляет серверное задание и его файлы.

## Локальный бот

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements-bot.txt
cp .env.example .env
nano .env
python bot.py
```

В `.env` задай `BOT_TOKEN`, `ALLOWED_USER_ID`, `PROCESSOR_URL` (например, `http://127.0.0.1:18080` для SSH-туннеля или HTTPS-адрес) и тот же `PROCESSOR_API_KEY`, что указан на сервере. `WHISPER_MODEL` выбирает модель, которую будет использовать удалённый обработчик.

Для фоновой работы бота можно использовать `tmux`:

```bash
tmux new -s speechparser
source venv/bin/activate
python bot.py
# Ctrl+B, D — отсоединиться
# tmux attach -t speechparser — вернуться
```

## Автономная расшифровка без воркера

`transcribe.py` — отдельная команда для локального распознавания через Whisper. Для неё нужны зависимости из `requirements-worker.txt` и FFmpeg:

```bash
python transcribe.py recording.mp4 --model medium --language ru
```

Команда загружает модель, распознаёт запись на текущем компьютере и сохраняет текст рядом с исходником.

## Настройки

| Переменная | Где задаётся | Назначение |
|---|---|---|
| `BOT_TOKEN` | локально | Токен Telegram-бота от [@BotFather](https://t.me/BotFather) |
| `ALLOWED_USER_ID` | локально | Telegram user ID, которому разрешён доступ |
| `PROCESSOR_URL` | локально, бот/CLI | URL worker: локальный адрес SSH-туннеля или HTTPS-адрес |
| `PROCESSOR_API_KEY` | локально и VPS | Общий секрет для авторизации запросов |
| `PROCESSOR_HOST` | VPS | Адрес прослушивания, по умолчанию `127.0.0.1`; в контейнере Compose задаёт `0.0.0.0` |
| `PROCESSOR_PORT` | VPS | Порт воркера, по умолчанию `8080`; при изменении согласуй публикацию порта и healthcheck в Compose |
| `WHISPER_MODEL` | бот/CLI и VPS | Модель Whisper, по умолчанию `medium`; в примерах `.env` задана `large-v3`. В запросах клиента можно переопределить через `--model` в CLI |
| `WHISPER_WORKERS` | VPS | Параллельные части транскрипции (`auto` или верхний предел числом) |
| `WHISPER_CPU_THREADS` | VPS | Потоки CPU на обработчик (`auto` или число); число потоков модели ограничено доступными CPU |
| `WHISPER_AUTOTUNE` | VPS | Автоподбор параллелизма по скорости: `1` (по умолчанию) или `0` |
| `WHISPER_AUTOTUNE_TIMEOUT_SECONDS` | VPS | Лимит времени одной пробы, включая загрузку модели; по умолчанию 180 секунд |
| `MTS_SESSION_ID` | только VPS | Cookie `access` для приватных записей МТС Линк |
| `TRANSCRIPTION_TIMEOUT_SECONDS` | локально и VPS | По умолчанию `10800` секунд: у клиента включает передачу, очередь и обработку; на VPS ограничивает обработку запущенного задания |
| `BOT_MAX_PENDING_JOBS` | локально | Максимум заданий бота, включая очередь и доставку результата; по умолчанию `32` |
| `MAX_UPLOAD_GB` | VPS | Лимит файла в десятичных ГБ, по умолчанию `10`; `0.25` = 250 МБ |
| `SERVER_MAX_CONCURRENT_JOBS` | VPS | Число одновременных заданий, по умолчанию `1` |
| `SERVER_MAX_PENDING_JOBS` | VPS | Предел заданий на загрузке, в очереди и обработке; по умолчанию `32`, не меньше числа одновременных заданий |
| `JOB_RETENTION_SECONDS` | VPS | Срок хранения исходника и результата после завершения задания, по умолчанию 86400 секунд |

При `WHISPER_WORKERS=auto` и `WHISPER_CPU_THREADS=auto` первое длинное задание на Linux автоматически сравнивает несколько конфигураций CPU. Например, при 16 доступных CPU и достаточном количестве частей проверяются `4 × 4`, `8 × 2` и `16 × 1` (обработчики × потоки). Для каждой конфигурации распознаётся одинаковый набор 30-секундных фрагментов из разных частей записи; выбирается вариант с наименьшим временем. Модель, язык, VAD и beam size совпадают с обычной расшифровкой. Параметры качества не меняются.

При автоматическом числе потоков конфигурации используют весь вычислительный бюджет без остатка: число обработчиков выбирается среди делителей числа доступных CPU. Например, при 16 CPU и пределе по памяти в 7 обработчиков резервный расчёт выбирает `4 × 4`, а не `7 × 2` с двумя нераспределёнными потоками. Это действует и при отключённом подборе и для коротких записей. Явное значение `WHISPER_CPU_THREADS` сохраняет ручное ограничение.

В логах каждой пробы выводятся время, средняя загрузка доступных CPU и пик RAM. Полностью распределённый бюджет не гарантирует постоянную загрузку 100%: операции модели масштабируются по-разному, а к завершению задания очередь чанков исчерпывается. Свободный обработчик получает следующий чанк сразу; выбор лучшей конфигурации определяется временем распознавания.

Подбор выполняется, когда число двухминутных частей не меньше числа доступных CPU и не меньше четырёх: на сервере с 16 CPU это запись длиннее 30 минут. Первый подбор может добавить несколько минут к обработке. Каждая проба запускается отдельно с ограничением адресного пространства по доступной RAM и таймаутом. Следующие конфигурации пропускаются, если измеренный расход памяти указывает на нехватку RAM. При ошибках, таймаутах или отсутствии речи используется обычный расчёт по CPU и памяти. Отмена задания завершает и активную пробу.

Результат сохраняется в `tmp/cpu_tuning/` (в Docker — volume `processor_data`) и используется в следующих заданиях. Ключ кэша учитывает модель, CPU, доступный параллелизм, версии библиотек и переменные вычислительных библиотек; перед использованием проверяется запас RAM. Для повторного подбора можно удалить соответствующий JSON из этой папки. Короткая проба даёт оценку производительности: выигрыш на полной записи может отличаться.

Ручное значение `WHISPER_WORKERS` или `WHISPER_CPU_THREADS` отключает подбор. Без подбора `WHISPER_WORKERS` остаётся верхним пределом, ограниченным прежней оценкой RAM; пробы могут проверить больше обработчиков с учётом фактически измеренной памяти. При `SERVER_MAX_CONCURRENT_JOBS` больше `1` подбор отключается, поскольку одновременные задания мешают сравнению скорости.

## Использование

1. Запусти обработчик на VPS и локальный `python bot.py`.
2. Отправь боту ссылку `https://my.mts-link.ru/...` или аудио/видео файл.
3. Бот покажет статусы и отправит готовую текстовую расшифровку без таймкодов.
4. Команда `/stop` останавливает текущую обработку и отправляет уже готовую часть текста.

При запуске бот автоматически регистрирует `/start`, `/help`, `/ping` и `/stop` с описаниями в Telegram. Команды доступны через кнопку меню и подсказки при вводе `/`. После обновления кода перезапусти `python bot.py`; настраивать команды вручную через BotFather не требуется.

Если воркер отключился, запрос завершился сетевым таймаутом, прокси вернул 502/503/504 или задание исчезло после перезапуска воркера, бот пишет короткий лог в консоль без сообщения об ошибке в Telegram. Локальное задание завершается и освобождает слот обработки; для файла удаляется временная копия. Автоматического повторного запуска нет. При недоступности воркера команда `/ping` также пишет только лог; при доступности отвечает в чат.

В статусе `Готово частей: 17/45 · 34,0/90,0 мин записи` минуты означают суммарную длительность готовых частей и всей записи. Это не прошедшее время и не прогноз ожидания. Аудиофрагменты МТС Линк располагаются по `relativeTime`: параллельные дорожки участников смешиваются, паузы сохраняются, повторяющиеся события исключаются. Итоговая длительность берётся из метаданных записи; при их отсутствии — из временной шкалы фрагментов. Микширование использует временный файл на диске и небольшие блоки в RAM.

Telegram Bot API ограничивает скачивание файлов размером 20 MB. Более крупные записи отправляй через `python cli.py /path/to/video.mp4` или ссылкой МТС Линк.

Задания бота выполняются по FIFO: ожидающая запись запускается после освобождения слота. Отправка предыдущего результата в Telegram не задерживает следующую расшифровку. `/stop` отменяет активное задание и ожидающие задания пользователя в текущем чате. Для параллельной расшифровки сохраняются полностью готовые части; после остановки они собираются по порядку записи. Незаконченные части не включаются в результат.

При нескольких одновременных заданиях расчёт бюджета CPU и RAM для распознавания учитывает `SERVER_MAX_CONCURRENT_JOBS` и `memory.high` cgroup. Это планирование ресурсов, а не отдельный жёсткий cgroup-лимит на каждый процесс. Для CPU-инференса обычно стоит оставить одно задание с параллельными частями. Изоляция каждого задания отдельным процессом сохранена: модель загружается заново для следующего задания, отмена завершает группу процессов вместе с FFmpeg и пробами. Compose запускает контейнер с `init: true` для уборки дочерних процессов.

Обе очереди хранятся в памяти и не восстанавливаются после перезапуска. Очередь воркера ограничена; при переполнении API отвечает HTTP 429. Временные каталоги обработки находятся внутри каталога задания, просроченные результаты убираются раз в минуту. Сетевые операции имеют собственные короткие таймауты отдельно от общего времени обработки; повторная отправка POST автоматически не выполняется.

Описание архитектуры, найденных проблем, исправлений и оставшихся ограничений: [AUDIT.md](AUDIT.md).

## Обновление

Обновляй код клиентов и воркера вместе. После обновления файлов репозитория установи зависимости нужного клиента:

```bash
# CLI
python -m pip install -r requirements-client.txt

# Telegram-бот
python -m pip install -r requirements-bot.txt
```

Перезапусти запущенный бот. На VPS дождись завершения текущих заданий и пересобери воркер:

```bash
docker compose up -d --build worker
```

При запуске воркера без Docker обнови зависимости из `requirements-worker.txt` и перезапусти `worker_server.py` с окружением из `.env.server`.

## Разработка и тесты

Зависимости разделены по способу запуска: `requirements-client.txt` для CLI, `requirements-bot.txt` для Telegram-бота, `requirements-worker.txt` для обработки. Docker устанавливает зависимости воркера. Для разработки и полного набора тестов `requirements.txt` объединяет зависимости всех компонентов:

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```
